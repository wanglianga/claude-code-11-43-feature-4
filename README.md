# 校园供餐多源数据质量与过敏原暴露覆盖分析工具

一款纯浏览器端（React 18 + TypeScript + Vite）的数据分析工具，帮助数据分析师判断五类来源数据——
**供应商成分、菜谱、厨房实际用料、餐次日志、学生饮食限制**——能否可靠关联，并量化过敏原暴露分析中
**多少记录有证据支持、多少存在候选待确认、多少因来源缺失无法判定**。

- 不调用任何真实学校服务，不上传个人数据；所有数据保存在浏览器本地 IndexedDB。
- 读取随项目提供的 CSV / JSON 样例（`public/sample-data/`，全部为虚构数据）。
- 未匹配记录一律计入「未知」，**不会被当成「没有过敏原」**；厨房 `PLANNED`（计划使用）不参与实际暴露计算。

## 一、核心设计

### 1. 三桶证据口径（每条领餐记录恰好落入一桶）

| 桶 | 含义 | 进入条件 |
| --- | --- | --- |
| 有证据支持的匹配 `CONFIRMED` | 链接链完整、原料解析有证据 | 供应商**精确编码**、**已批准别名**或分析师**人工确认**，且餐次/用料/限制链路完整 |
| 存在候选但需确认 `CANDIDATE_PENDING` | 有名称/规格/单位/成分候选，但未确认 | 候选**确认前不进入正式统计**，不低报暴露 |
| 来源缺失无法判定 `UNKNOWN_MISSING` | 来源缺失或链接断裂 | 区分空餐次、关联不存在、时间无法归属、批次未到齐、限制为空/未生效等具体原因 |

精确匹配与上下文候选**并行**：只有精确编码/批准别名自动生效；候选经分析师确认后才复用该决定。

### 2. 字段四态（不折叠成同一个失败数）

- `FIELD_NOT_PROVIDED` 源文件未提供该字段（如乙校供应商文件没有 `cert_no` 列）
- `VALUE_EMPTY` 字段值为空（甲校部分行 `cert_no` 留空）
- `REF_NOT_FOUND` 关联对象不存在（领餐→餐次、餐次→菜谱、限制学生→领餐）
- `BATCH_PENDING` 来源批次尚未到齐（`kit-b-2`，预期 6 行）

### 3. 不可变运行与版本固定

每次分析运行固定引用：**全部输入文件 SHA-256、映射版本+修订号、规则版本（rules-v1）**。
补发旧数据或修改映射后生成的是**新运行**，历史运行不被静默改写；「运行对比」页展示三桶迁移矩阵、
覆盖率变化与质量问题增减。

### 4. 映射乐观锁（多标签页）

保存映射时重新读取 IndexedDB 校验修订号；另一标签页已提交更高版本时，后提交者保存被拒绝并提示重载，
已确认映射不会被覆盖（同时通过 `BroadcastChannel` 主动推送版本变化）。

### 5. 跨校供餐指标可比性分析（本次新增）

在既有领餐级成分判断之上，独立增加**总体核对 → 指标计算 → 可比范围分析**三层，
回答「学校之间的成分记录比例差异来自实际记录、资料缺口，还是供餐结构不同」。
本功能为数据覆盖与指标口径分析，**不评价哪所学校更安全，也不根据群体记录推断学生实际摄入**。

**统计单位**：固定为「学校 + 窗口 + 业务日 + 餐别」定位的一次供餐记录；同一窗口同餐别的多段开放时间
合并为同一记录。菜品行、原料行和发餐份数**不作分母**。

**来源登记**（4 类新来源，各批次在清单中声明完成范围 `declaredScope`）：

| 来源 | 内容 |
| --- | --- |
| 窗口供餐登记 `window_registry` | 应覆盖的窗口及供餐周期（含一条重叠调整单，去重后生效） |
| 窗口发餐日志 `service_log` | 实际发餐记录（含重复上报行与计划开餐行） |
| 停业/零供餐依据 `closure_evidence` | 明确停业或零供餐的依据 |
| 窗口用料台账 `window_usage` | 按窗口/餐别/日期的实际用料（成分判断输入） |

**总体核对**：应报窗口不一定实际供餐；计划开餐表不能证明发生过供餐；有实际发餐但用料缺失进入未知；
明确停业/零供餐不计入实际供餐分母；没有日志且没有停业依据则保留为**未解释缺口**（总体尚不完整）。
重复上报（同 `log_id`）与登记表重叠（多对多连接）**不复制供餐记录**。

**成分判断**（复用主服务已有的厨房简称解析结果）：对选定的一种过敏原，将有实际用料依据的**含有**、
足以判断且**未发现**、证据不足及冲突的**无法判定**分别计算。部分原料未知但已有一条充分含有依据时
仍可确认含有；只有完整到足以排除的资料才可归入未发现，缺报不能默认不含。每种成分各自按供餐记录计算，
不把各成分命中数相加当总餐数。

**指标与边界**：展示已核实记录中的比例时明确标注只覆盖已核实子集，同时报告实际供餐总量是否已知、
资料完整度和未知范围。总体已完整时给出比例**下界**（已确认含有/实际供餐总量）与**上界**
（计入尚不能判定的记录）——这只是未知记录不同取值下的边界，**不是置信区间，也不是学生暴露率**；
总体仍有未解释缺口时不套用同一公式给出貌似完整的学校比例。

**可比范围分析**：先列各餐别原始计数、比例和覆盖，再解释总体构成。选择**直接标准化**
（共同参照餐别权重，固定参照构成，切换学校不随之改变；参照中某层缺少可核实资料时不能完成该校的
完整调整值；权重随比较范围显式归一化）。另一种方法**分层匹配**（只在双方都有充分资料的餐别中比较）
适用于缺报严重、只需局部可解释结果的场合，但会舍弃真实供餐记录且结论不外推到全校——本工具选择
直接标准化，牺牲的是：某校某层缺少可核实资料时不给出该校任何单一调整数值（宁可标注
「无法完成完整调整」，也不用删层重归一化的伪同口径数值）。不同学校未知范围很大或边界重叠时，
不强行给出确定的高低结论。

**补传影响预览**：补传一个缺报窗口可能同时改变分母、未知比例和可比范围，先展示这些差异再生成新运行；
由未知转成含有只改变已有记录的判断（分母不变），不会既新增分子又重复新增已经存在的供餐记录。
旧运行继续解释当时的资料覆盖与参照；另一标签页提交补传后，本页旧结果标记为过期，不作为新范围结论。

## 二、目录结构

```
public/sample-data/          随项目提供的样例输入（CSV/JSON + manifest + 种子映射）
  manifest.json              批次清单（含晚到批次 sup-a-2、未到齐批次 kit-b-2、补传批次 wul-a-2/log-a-2/wul-a-3）
  standard_ingredients.json  10 种标准原料及其过敏原
  seed_mappings.json         初始映射（批准别名 + 人工确认决定）
  schoolA/ schoolB/ meal/ diet/   领餐级来源（供应商/菜谱/厨房/餐次/领餐/饮食限制）
  registry/                  供餐指标来源（窗口登记/发餐日志/停业依据/窗口用料 + 3 个补传批次）
src/
  lib/        CSV 解析、SHA-256、IndexedDB 封装、数据加载、导出、批次统计、供餐导出
  engine/     规则、上下文索引、质量检查、匹配引擎、运行引擎与对比/预览、供餐分析引擎（纯函数，可单测）
  state/      React 全局状态、IDB 持久化、乐观锁、补传激活与跨标签页过期通知
  components/ 共享组件（徽标、抽屉、覆盖图、供餐可视化、记录下钻）
  pages/      总览 / 来源批次 / 映射工作台 / 质量检查 / 分析运行 / 运行详情 / 运行对比 / 供餐指标 / 跨校比较
Dockerfile + docker-compose.yml + nginx.conf   一键静态部署
```

## 三、本地启动

### 方式 A：Node 开发服务器（推荐用于本地开发）

要求 Node.js 22（容器内固定入口 `/opt/node-22/bin/node`）。

```bash
npm install --registry=https://registry.npmmirror.com
npm run dev        # http://localhost:5173
```

生产构建与本地预览：

```bash
npm run build      # 类型检查 tsc -b + vite build，产物在 dist/
npm run preview    # http://localhost:4173 静态预览（含 SPA 回退）
```

> 必须通过 HTTP 服务访问（需要 `fetch` 读取样例数据），不要直接双击打开 index.html。

### 方式 B：Docker / Compose 一键启动

```bash
docker compose up --build
# 打开 http://localhost:8080
```

多阶段构建：node:22-alpine 构建静态资源 → nginx:1.27-alpine 托管（已配置 SPA 路由回退）。
停止：`docker compose down`。

## 四、测试账号与隐私说明

本工具**没有登录体系、没有后端、没有测试账号密码**：

- 样例学生均为匿名学号（`S-1001` … `S-1023`、`S-9999`），由校医维护的饮食限制按匿名学号生效。
- 所有映射、人工确认、分析快照与运行结果仅写入浏览器 IndexedDB（库名 `campus-meal-dq`）。
- 「分析运行」页提供「重置工作区」，可清空本地数据并恢复随项目提供的种子映射。
- 可在浏览器 DevTools → Application → IndexedDB 中核查全部本地数据，不存在任何网络上报。

## 五、验证方式（建议操作路径）

1. **总览页**：查看 11 个领餐级来源批次的输入/有效/重复/关联/未知行数与三桶覆盖环形图；点开「指标详情」查看分子、分母、排除条件、来源范围。
2. **来源批次页**：打开 `sup-b-1` 看到 `cert_no` 为「源文件未提供」；打开 `sup-a-1` 看到 3 行「字段值为空」；打开 `kit-b-2` 看到「批次尚未到齐」；可逐行下钻原始行。
3. **质量检查页**：核对重复键、缺失键、单位冲突、时间无法归属、多对多连接五类问题并下钻原始行。
4. **映射工作台**：在「菜谱/厨房简称」中找到待确认候选「芝麻」（影响餐次 MS-A-0901-D / 领餐 SV-006），
   点「预览影响」→ 看到候选 1→0、确认 4→5、未知 19 不变 → 「保存并生成新运行」。
5. **分析运行 → 运行详情**：三桶筛选、逐层下钻（计算轨迹、参与计算的厨房实际用料原始行与映射决定、领餐原始行），
   导出 JSON（含运行编号、口径摘要、未知范围与免责声明）或 CSV。
6. **运行对比**：选择两个运行，查看桶位迁移矩阵与覆盖率变化；旧运行保持不变。
7. **多标签页冲突**：再开一个浏览器标签页，在两个标签页同时编辑映射，后保存者收到版本冲突横幅且保存被拒绝。
8. **供餐指标页**：默认成分「乳」、范围 9/1–9/5。查看两校总体核对（甲校 5 个未解释缺口、乙校完整）、
   分层指标（早餐/午餐/晚餐各自的实际供餐、已核实、含有、未知、边界），点击分层行「查看记录」下钻到
   每条供餐记录的纳入/去重/判断原因与原始行。
9. **跨校比较页**：查看固定参照构成（早餐 30%/午餐 40%/晚餐 30%）、各餐别原始计数与已核实比例、
   总体构成（辛普森反转提示）、直接标准化调整值（甲 34.0% vs 乙 47.3%，但边界重叠不强行结论）、
   可比范围（留下与舍弃的记录清单）。
10. **补传预览**：供餐指标页「补传批次」中对 `wul-a-2` 点「预览影响」→ 分母 37→37 不变、未知 3→1、
    含有 0→1（9/4 晚餐确认含乳）→「确认补传并生成新运行」；再对 `log-a-2` 预览 → 分母 +5、缺口 5→0。
    过滤日期到 9/4–9/5 时，补传前甲校晚餐层「参照缺层」无法完成调整，补传后可比范围扩大。
11. **跨标签页补传**：两个标签页同时打开供餐指标页，在一个标签页确认补传后，另一标签页收到
    「旧结果不得作为新范围结论」横幅，需「应用新范围并重新计算」。

基于当前样例与种子映射（`npm test` 中以断言固化）：

  （SV-004 乳、SV-008 蛋、SV-009 麸质、SV-010 乳），确认安全 0 条。

  晚到批次中同条码变成含芝麻的新配方，系统拒绝自动合并并降级为待确认候选）。
- 确认「芝麻」候选后：候选 1→0、确认 4→5、未知保持 19；`diffRuns` 输出迁移矩阵
  `CANDIDATE_PENDING → CONFIRMED = 1`，变化记录仅 SV-006。

  乙校应覆盖 20 = 实际供餐 17 + 明确停业 2（W1 早餐 9/1–9/2）+ 明确零供餐 1（W2 晚餐 9/4）。
- 餐别内已核实比例（含有/已核实）：早餐 甲 60.0%（6/10）< 乙 66.7%（2/3）；
  午餐 甲 40.0%（2/5）< 乙 60.0%（3/5）；晚餐 甲 0.0%（0/2，另有 3 条未知）< 乙 11.1%（1/9）。

  差异来自供餐结构（甲校已核实记录 58.8% 是早餐，乙校 52.9% 是晚餐）。
- 直接标准化（参照 30/40/30）：**甲 34.0% < 乙 47.3%**——调整值顺序与餐别内一致、与合并相反；
  但甲校晚餐层内缺报且调整边界重叠（甲 34.0%–52.0% vs 乙 47.3%），不强行给出确定的高低结论。
- 乙校总体完整，全校比例边界 [35.3%, 35.3%]；甲校有缺口，不套用完整公式。
- 补传 `wul-a-2`（甲 W1 晚餐 9/4–9/5 用料）：分母 37→37 不变、未知 3→1、含有 0→1；

  调整边界不再重叠，乙校调整值高于甲校。
- 过滤 9/4–9/5：补传前甲校晚餐层实际供餐 2 条但全部未知（参照缺层），无法完成完整调整值；
  补传 `wul-a-2` 后该层可核实，可比范围从「早餐、午餐」扩大到「早餐、午餐、晚餐」。

## 八、口径与防误读声明

导出文件内置免责声明：**「未知/无法判定」表示当前来源缺少证据，不等于该餐确认不含过敏原；
接收方不得据此作出『无过敏原』结论。** 导出 JSON 同时携带运行编号、规则/映射版本、全部输入文件哈希、
口径摘要、完整未知范围与每条领餐的评估明细。
